# Phase 2.11 architecture audit

- Issue: [#127](https://github.com/AdriGB/Nexus/issues/127)
- Scope: architecture only; no behavior changes
- Baseline: `main` at the start of Phase 2.11

## Executive summary

Nexus substantially follows ADR 0001: it is a modular monolith, the bridge is
transport-only, domain rules generally live below the simulation facade, and
the tick order is discoverable in `pipeline.rs`. No critical boundary violation
was found.

The main exception is orchestration duplication. `run_step`,
`run_profiled_step`, and `run_profiled_autonomy_step` encode overlapping tick
lifecycles, while `run_autonomy` and `profile_autonomy` separately encode the
entity loop. Their phase order has already drifted in small ways. This is the
first high-priority refactor because every benchmark and scheduler change would
otherwise have to preserve several implementations.

`Simulation` remains both the state container and the integration service for
several domains. This is acceptable during incremental extraction, but event
translation, relationship consequences, lifecycle integration, and household
storage are now distinct responsibility clusters. They should be extracted
only behind concrete outcome contracts, not merely to shorten the file.

## Audit method and severity

The audit inspected `simulation/mod.rs`, `simulation/pipeline.rs`, all autonomy
modules, `households.rs`, `events.rs`, `dependents.rs`, `kinship.rs`,
`lifecycle.rs`, and all bridge modules. It traced imports and visibility,
identified state mutation sites, compared execution paths, and noted structural
scans and allocations. It did not attempt to measure runtime cost.

- **Critical:** breaks determinism or ownership now; fix before other work.
- **High:** makes safe scale work unreliable or creates material rule coupling.
- **Medium:** a concrete boundary or scale risk requiring evidence before change.
- **Low:** surface-area or clarity debt with limited immediate risk.

## Required invariants

| Owner | Invariant |
| --- | --- |
| Simulation | Tick, entity IDs, event IDs and counters are monotonic |
| Simulation / entity | Entity IDs are unique and the collection remains sorted for binary search |
| Autonomy | Knowledge enters memory only through perception or explicit interaction |
| Inventory | Quantities and capacity arithmetic cannot underflow or exceed capacity |
| Households | Entity membership and household membership/storage access agree |
| Genealogy | Parentage is registered consistently and derived relations invent no links |
| Events | IDs are nonzero and causal references identify already-created events |
| Spatial | Snapshots and buckets describe entity positions at their consumption phase |
| World integration | Resource mutations advance `world_revision` consistently |
| Pipeline | Normal, phase-profiled and autonomy-profiled ticks produce equal logical state |

## Dependency map

```text
web UI
  -> WASM facade (`lib.rs`)
      -> bridge DTO/serialization modules
          -> simulation query facade + world queries

simulation pipeline
  -> Simulation state/integration facade
  -> physiology, dependents, households, grief
  -> lifecycle and relationship maintenance through Simulation helpers

Simulation integration facade
  -> autonomy -> perception / decision / action / social
              -> spatial + pathfinding + world
  -> households -> entity + inventory + genealogy + world
  -> events -> world resource kinds
  -> lifecycle -> entity + world
  -> kinship -> genealogy + entity
```

The bridge does not feed DTOs back into engine rules. Domain modules do not
depend on the bridge or web UI. The notable coupling is inside the simulation
boundary, where multiple domains mutate fields stored directly on `Entity` and
`Mind`; the integration facade currently enforces the cross-domain ordering.

## Responsibilities retained by `Simulation`

The following clusters are candidates for gradual extraction:

1. **Autonomy integration:** building household contexts, collecting outcomes,
   feeding dependents, and translating autonomy outcomes into domain actions.
2. **Relationship consequences:** interaction events, affinity events, food
   sharing consequences, partnership formation and dissolution.
3. **Lifecycle integration:** death collection, birth materialization, genealogy
   registration, household assignment and causal event emission.
4. **Household storage facade:** access validation followed by inventory/storage
   transfer across two owners.
5. **Event translation:** repeated construction of central event envelopes.

These responsibilities should not all move into `events` or `pipeline`.
Pipeline owns order, domains own rule meaning, and the composition root may keep
translation between stable domain outcomes and the central event stream.

## Public surface review

The public API visible outside `simulation` is mostly intentional: bridge and
WASM code require entity views, profiles, statistics and simulation commands.
The highest-value visibility review is internal to `autonomy`, where stage
implementation types are re-exported at several visibility levels. Closing
them now would create noise before the duplicated execution paths are unified.

Recommended rule: after every extraction, run `rg` over each changed export,
narrow it to its actual consumers, and keep test helpers test-only. Do not add a
generic domain API merely to replace a concrete `pub(crate)` item.

## Prioritized refactor queue

1. **High — one tick pipeline:** execute one ordered lifecycle with optional
   instrumentation; keep normal/profiled parity coverage.
2. **High — one autonomy loop:** route sampled timing through the same entity
   update and outcome aggregation path.
3. **Medium — stable instrumentation phases:** correct phase names, add counters
   and establish reproducible scenario output.
4. **Medium — named domain outcomes:** replace positional autonomy tuples and
   isolate relationship/lifecycle consequence contracts.
5. **Medium — invariant coverage:** add focused tests for entity ordering,
   household membership, event IDs and spatial snapshot timing.
6. **Medium — benchmark structural risks:** quantify household contexts, global
   maintenance scans, kinship allocations and event-summary queries.
7. **Low — visibility sweep:** narrow internal exports based on observed callers.
8. **Conditional — architectural enforcement:** add dependency tests only where
   review repeatedly fails to protect a boundary.

Estado a 2026-08-30: los puntos 1–5 y el 8 están resueltos en `main` (A01–A05,
A07, A13, A14). Siguen abiertos el 6 (medir riesgos estructurales, A08–A10) y el
7 (visibility sweep, A11). Véase el registro destilado al final.

### Trampas ya codificadas

Convenios que hoy protege un test o el propio código. Se listan para no
redescubrirlos.

- `src/simulation/tests/**` **puede** importar `crate::bridge` (verifica DTOs);
  el guard de dependencias ignora ese directorio a propósito.
- El stripper de comentarios necesita `r##"` cuando el contenido lleva `r#"`, y
  los alias `as` se resuelven por segmento, no globalmente.
- `conception_scans` sólo cuenta en días múltiplo de `TICKS_PER_DAY`, y
  `household_migration_scans` cuenta `1` por tick en lugar de `N`: `plan_daily_*`
  es O(N) pero corre una vez al día, y `1` explica mejor la cadencia.
- Los contadores del funnel social sólo se pueblan en runs perfilados porque la
  ruta de producción pasa `None`. Pero el camino que el benchmark cronometra es
  `profile_run`, que sí los incrementa: cuatro sumas por par candidato, unas
  556k por tick a 10k. **El funnel y el tiempo medido en esa misma pasada no son
  independientes**, aunque eso no mueva el reparto del paso por entidad.
