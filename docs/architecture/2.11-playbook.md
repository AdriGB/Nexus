# Phase 2.11 playbook — what remains and how to do it

Scope: practical companion to `2.11-audit.md` and `tick-phases.md`.
It does not replace the audit. It maps the exact current tick, the measured
scale risks, the determinism surface, and the persistence surface, so that
2.11.6 (scheduler), 2.11.7 (state hash), 2.11.8 (persistence) and 2.11.9
(quality sweep) can be executed as small, verifiable issues.

Status at time of writing: 2.11.1–2.11.5 landed. Phase 2.11.7 (canonical
state hash, scale goldens, cross-platform hash parity Windows <-> Ubuntu in
run 33891754349) is sealed and merged (#217-#222).
Phase 2.11.6 (scalability & multi-rate scheduling) begins with empirical
data: **no optimization without a number, no scheduler without a hash**.

> Update 2026-09-04 (Post run 33891754349):
> Full benchmark run 33891754349 verified byte-identical state hashes across
> all 9 scenarios between Windows x64 and Linux x64 (Ubuntu).
> Empirical timings from this run show that cold maintenance phases
> (`dependent_care` + `households` + `mortality`) total <0.36% of tick time in
> `baseline-10000` (1.2 ms / 344 ms) and <0.03% in `lineage-1000` (28.7 µs / 84.7 ms).
> **97.5% to 99.8% of simulation time is spent in Autonomy**, specifically:
> - `planning_us` (A* pathfinding): 83.8 ms/tick in `lineage-1000` (~280,000 nodes/tick)
> - `perceive_entities_us`: 129.1 ms/tick in `baseline-10000`
> - `social_pass_us`: 163.5 ms/tick in `baseline-10000`, 38.1 ms/tick in `lineage-1000`
> 2.11.6 begins by attacking these actual bottlenecks, not cold maintenance scans.

## 2. Scale inputs for 2.11.6 (Data-Driven from Run 33891754349)

### 2.1 Reality check on cold-path maintenance scans

Earlier drafts suspected high cost in un-gated maintenance passes. Actual
measurements from the full benchmark suite disprove this:

| Phase | `baseline-1000` | `baseline-10000` | `lineage-1000` |
|---|---|---|---|
| `autonomy` | 22,572.0 µs (99.3%) | 341,394.1 µs (99.2%) | 84,506.2 µs (99.8%) |
| `dependent_care` | 14.5 µs (0.06%) | 965.5 µs (0.28%) | 6.9 µs (0.01%) |
| `households` | 19.0 µs (0.08%) | 195.0 µs (0.06%) | 18.3 µs (0.02%) |
| `mortality` | 2.7 µs (0.01%) | 65.1 µs (0.02%) | 3.5 µs (0.00%) |
| `relationships` | 65.1 µs (0.29%) | 719.3 µs (0.21%) | 119.7 µs (0.14%) |
| `spatial_index` | 11.2 µs (0.05%) | 193.5 µs (0.06%) | 12.0 µs (0.01%) |

Key code realities (post-#218):
- `grief::process_witnessed_deaths` already early-returns immediately on `deaths.is_empty()` (`grief.rs:32-34`).
- `snap_infants_to_caregivers` filters infant indices and uses `binary_search_by_key`; it does **not** build a `HashMap`.
- `reassign_orphaned_dependents` filters infant/child indices and uses `binary_search_by_key`; it does **not** allocate a living `HashSet`.
- `synchronize_dependent_memberships` operates on filtered infant/child indices via `binary_search_by_key`.
- In `settle_basic_inheritances`, allocating `living: HashSet` is a no-op when `dissolutions.is_empty() || deaths.is_empty()`. Even with that allocation, the entire `households` phase takes only 195 µs at N=10,000.

**Rule: Do not create vanity PRs on cold maintenance paths.** Eliminating them completely yields <0.36% speedup, far below measurement noise.

### 2.2 Where 99% of CPU time actually goes

From `autonomy_breakdown`:

1. **`planning_us` (A* Pathfinding & Goal Evaluation):**
   - In `lineage-1000`: **83,810 µs / tick** (79.5% of entity pass). Expands 27,941,259 nodes across 28,899 searches per 100 ticks (~280k nodes/tick!).
   - In `dense-social-1000`: **88,556 µs / tick** (27.9M nodes).
   - In `pathfinding-heavy-1000`: **86,028 µs / tick** (26.8M nodes).
   - In `baseline-10000`: **47,550 µs / tick** (5.9M nodes).
   - Cause: `DEFAULT_MAX_ITERATIONS = 50_000` without per-tick node/search budgets, combined with 1-tick idle replanning loops on unreachable targets.

2. **`perceive_entities_us` (Spatial queries and known-entity updates):**
   - In `baseline-10000`: **129,143 µs / tick** (62.6% of entity pass).
   - In `dense-social-1000`: **21,335 µs / tick**.
   - In `lineage-1000`: **20,875 µs / tick**.
   - Cause: 10,000 entities querying the spatial grid and updating known entities every tick even while traversing existing paths.

3. **`social_pass_us` (Pairwise interaction evaluation):**
   - In `baseline-10000`: **163,530 µs / tick** (47.5% of total tick).
   - In `lineage-1000`: **38,125 µs / tick**.
   - Cause: Millions of candidate pairs scanned and evaluated across visible entities.

### 2.3 Priority execution order for 2.11.6

1. **Pathfinding Budgeting & Planning Throttle (Targeting `planning_us`):**
   - Add deterministic per-tick search/node budgets in `PathfindingWorkspace`.
   - Contextual search limits (`LOCAL_SEARCH_LIMIT` for wander/adjacent seeks vs `GLOBAL_SEARCH_LIMIT`).
   - Planning backoff cooldown on failed paths to break 1-tick replanning loops.
   - Deterministic goal prioritization when budgets are exhausted (survival > social/explore).
2. **Perception Interleaving / Staggering (Targeting `perceive_entities_us`):**
   - Interleave non-critical entity perception for agents moving along valid paths (`(id + tick) % K == 0`).
3. **Social Pass Candidate Optimization (Targeting `social_pass_us`):**
   - Further optimize pair filtering and eliminate remaining linear lookups.

## 3.3 Original audit (pre-branch reference)

Good news, verified by reading the code:

- No `rand`, `thread_rng`, `getrandom`, `SystemTime`, `rayon`/`par_iter` in simulation logic. All randomness is `mix64(seed, id, salt, tick)` in `lifecycle.rs:294-312` and `resources.rs:5-12`.
- All `Instant::now` uses are behind `Option<Profile>` (`autonomy/mod.rs`, `simulation/mod.rs:744,862,946`, `pipeline.rs:56,95,302`). Production path (`run_step`) never touches the clock. Parity tests already assert step == profiled step.
- `entities` and `households` are append-only `Vec`s sorted by id (`mod.rs:696-732`, `households.rs:626-634`); `retain` preserves order. `binary_search_by_key` is therefore valid everywhere.
- `BTreeMap` was already chosen where iteration matters (`genealogy.rs:19-20`, `mod.rs:321-334` for `caregiver_index`), with explicit comments.

Residual risks to fix as part of the hash work:

1. ~22 `HashMap`/`HashSet` (std, `RandomState`) remain (`dependents.rs:13,69`, `households.rs:84,202,210,344-345,464,530`, `grief.rs:36`, `social.rs:475`, `lifecycle.rs:226`, `mind.rs:199` persistent `known_chunks`). None is *iterated* to mutate state today (only `get/contains/entry/len`), but any future `for (k,v) in map` would be nondeterministic. Hottest: `social.rs:475` (rebuilt every tick — replace with `binary_search`).
2. `known_chunks: HashSet<u32>` (`mind.rs:199`) is the only persistent hash-set in state — sort before hashing, consider `BTreeSet`.
3. Float tie-breaks: `decision.rs:471-474` picks max utility with `max_by(total_cmp)` and no explicit goal tie-break; `lifecycle.rs:350,388` sorts spawn candidates by distance only (`sort_unstable`). Add total tie-breaks (`(dist, index)`, goal discriminant) before freezing golden hashes.
4. World `f64` fields (`altitude/moisture/temperature`) should not be hashed raw if the hash must hold across wasm/native — hash `Terrain as u8`, quantize or exclude the floats.

### `SimulationStateHash` proposal

- Hasher: fixed chain reusing existing `mix64` (`h = mix64(h ^ piece)`), never `std` `DefaultHasher`.
- **Include, in fixed order:** `seed, tick, next_entity_id, next_household_id, births, deaths, food_consumed, world_revision`; per entity in id order (pos, sex, lifespan, `hunger/health.to_bits()`, age, path+index, activity, pregnancy, postpartum, movement credit bits, mother/father/caregiver/partner/household, personality bits, inventory, action_tick, mind: goal/plan/goal_since/visible/grief/memory with `known_chunks` sorted); per household in id order; `genealogy.records` in order (exclude derived `children` index or iterate its `BTreeMap` canonically); world `resources`/`renewable` per tile index + `terrain as u8`.
- **Exclude:** `population_cache`, `caregiver_index`, `spatial_grid`, `pathfinding_workspace` (derived/scratch + `Cell` counters), `paused` (UI control), `recent_events` content (bounded eviction — keep a separate event hash if needed), all `*_us/*_ns` profiles, `WorkCounters`, `StateGauges`, `UtilityScores`/explanations (overwritten each tick).
- Tests: same-seed-same-hash across runs; full-run vs chunked-run hash equality; profiled-on/off hash equality; debug/release logical equality; `debug_assert!(ids sorted)` before hashing.

## 4. Persistence inputs for 2.11.8

### Persist YES

- `Simulation`: `tick, paused, entities (Vec, id-ordered), next_entity_id, seed, births, deaths, food_consumed, world_revision, genealogy, households, next_household_id, recent_events` (`mod.rs:316-347`).
- `Entity` (`entity.rs:62-87`): all fields including `path/path_index`, `pregnancy`, `postpartum_until_tick`, `movement_credit`, `mother/father/caregiver/partner/household`, `personality`, `inventory {capacity, amounts:[u16;4]}`, `action_tick`.
- `Mind/Memory` (`mind.rs:517-528,196-204`): `perception_radius, current_goal/plan/plan_index, goal_since_tick, visible_entities (sorted), grief (sorted)`; all of `Memory` (`known_resources, known_chunks (serialize sorted), failed_exploration, known_entities (id-ordered), known_dead (ordered), conflict_history (ordered)`).
- `Household` (`households.rs:18-44`): identity, ticks, migration, inheritance, residence, storage. Membership itself is derived from `Entity.household_id` via `members_of`.
- `Genealogy.records` (append-only, includes the dead). `children` index is rebuildable — persist `records` only in v2, or both + assert in v1.
- `Events`: `VecDeque` content in id order + `capacity` + `next_id` + `total_created` (`events.rs:192-198`).
- World mutable layer: `width/height, tiles[].terrain (+ optionally quantized climate), resources[] per index, renewable[]`.

### Persist NO (rebuild always)

`population_cache`, `caregiver_index`, `SpatialGrid` (has `Cell` counters), `PathfindingWorkspace`, all profiling/counters/gauges. `Kinship` has no state (pure queries).

### Gaps to close for a v1 snapshot

1. Nothing persistent is `serde` today — only world value types (`world.rs`), counters/gauges, and bridge DTOs are `Serialize`. Prefer versioned `SnapshotV1_*` DTOs over deriving on internals (keeps `HashSet`/`VecDeque`/`BTreeMap`/`f32` out of the format).
2. `Grid` does not store its own `seed`/`sea_level` (`generation.rs:4`, `lib.rs:91-99` drop them) — add to header: `format: "nexus-snapshot/v1"`, engine phase, sim `seed`, world seed + dims + sea level, `tick`, checksum.
3. Normalize on write: sort entities/households/records/memories, `HashSet→sorted Vec`, `VecDeque→Vec` in id order; preserve `Inventory.capacity` and `RecentEventHistory.capacity/next/total`.
4. Load order + validation: header/checksum → `Grid` (len, indices, walkability) → re-`detect_regions` and compare → simulation scalars (`next > max(id)`, tick ≥ all referenced ticks) → entities (bounds, `health>0`, `path_index ≤ len`, partner symmetry, caregiver/household/parents exist, pregnancy `due > tick`, affinity ranges, grief `ends > tick`) → genealogy (`children == rebuild(records)`) → households (ordered, residence walkable, dissolved ≥ formed) → events (len ≤ capacity, ids increasing and `< next_id`, ticks ≤ snapshot tick) → **always** rebuild index/grid/workspace, zero profiling.

Bridge DTOs (`bridge/*.rs`) are lossy projections (counts instead of contents, labels instead of enums) — do not reuse them as the snapshot format.
